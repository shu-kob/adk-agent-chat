# 📗 SPECIFICATION 追補 — 測定カバレッジとレート制限対応 (ADDENDUM v4)

本ドキュメントは `docs/SPECIFICATION.md` に対する**追補仕様（第4版）**である。

Phase 1 の初回実測（`run_id: 20260830_153547`）を分析した結果、評価基盤の実装自体は仕様どおり動作しているが、**測定結果の解釈を誤らせる構造的な欠陥**が判明した。本追補はその修正を指示する。

## 発見された問題の要約

初回実測では 270 試行中 **34 件が API エラー（うち 33 件が HTTP 429 RESOURCE_EXHAUSTED）** となった。エラーは `gemini-3.7-flash` に集中し（34 件中 32 件）、同モデルの `negative_constraint` カテゴリでは 10 ケース中 4 ケース（`neg_02`, `neg_03`, `neg_04`, `neg_05`）が全 3 試行ともエラーとなり、**一度も測定できていない**。

追補 v1 の仕様に従い、エラーはスコア 0 として集計に混ぜていない。この判断自体は正しい。しかし現在の集計はエラーとなったケースを**分母からも除外**しているため、以下が発生している。

- `gemini-3.7-flash` の `negative_constraint` スコア 91.1% は、測定できた 6 ケースのみの平均値である
- レポート上は `91.1% (4/10)` と表示され、10 ケースを評価したように読める
- 結果として、**答えられなかったケースが多いモデルほどスコアが高くなる**

生成された考察レポートは、この数値を「ネガティブ制約に対する抑制力が高い」と解釈していた。実際には該当ケースで応答を得られていない。

**測定できなかったという事実が、集計の過程で不可視になっている。** これが本追補で解決すべき中心的な課題である。

## 1. レート制限への対応

### 1.1 リトライ機構

#### 要件

- API 呼び出しが HTTP 429 (`RESOURCE_EXHAUSTED`) を返した場合、**指数バックオフによるリトライ**を行う。
  - 初回待機時間、最大リトライ回数、バックオフ倍率を設定可能にする
  - 既定値: 初回待機 2 秒、最大 5 回、倍率 2.0、ジッタあり
  - 環境変数 `EVAL_RETRY_MAX`（既定 `5`）, `EVAL_RETRY_BASE_SEC`（既定 `2.0`）で調整可能とする
- リトライは 429 および一時的なネットワークエラー（タイムアウト、503 等）に限定する。
  - 400 系のうち 429 以外（不正なリクエスト、認証エラー、モデル未解決など）はリトライせず即座に失敗として記録する
  - リトライ対象のエラー種別を実装内で明示的に列挙すること
- リトライ回数を試行レコードに `retry_count` として記録する。
- **リトライで成功した試行は成功として扱う**。ただしリトライが発生した事実は保持する。

### 1.2 スロットリング

#### 要件

- モデルへの呼び出し間隔に下限を設ける。
  - 環境変数 `EVAL_REQUEST_INTERVAL_SEC`（既定 `1.0`）で設定
  - 同一モデルへの連続呼び出しの間に最低この間隔を空ける
- 並列実行を行っている場合は、モデル単位の同時実行数に上限を設ける。
  - 環境変数 `EVAL_MAX_CONCURRENCY`（既定 `1`）
  - 既定値 1 は逐次実行を意味する。測定の安定性を実行速度より優先する

#### 実行時間への影響について

スロットリングにより総実行時間は増加する。初回実測は 270 試行で約 20 分（1209 秒）であった。この増加は許容する。

**評価基盤において、実行速度は測定の正確性に優先しない。** レート制限による欠測は、実行時間の短縮では取り返せない情報の損失である。

### 1.3 事前チェックへの追加

`eval/precheck.py` の疎通確認において、以下を追加する。

- 各対象モデルに対して**連続した複数回**（既定 3 回）の ping を行い、レート制限が発生しないことを確認する。
- 429 が発生した場合は警告として報告し、`EVAL_REQUEST_INTERVAL_SEC` の増加を促すメッセージを出力する。
- 実行を中断するかは設定に委ねてよいが、既定では警告のうえ継続とする。

## 2. 測定カバレッジの可視化

レート制限対応を行っても、エラーが完全にゼロになる保証はない。したがって、**欠測が発生した場合にそれが必ず見える**構造が必要である。

### 2.1 カバレッジ指標の定義

以下を新たな指標として定義し、集計に組み込む。

| 指標 | 定義 |
| :--- | :--- |
| `measured_cases` | 少なくとも 1 試行が成功したケース数 |
| `total_cases` | 対象カテゴリの有効ケース総数 |
| `case_coverage` | `measured_cases / total_cases` |
| `fully_measured_cases` | 全試行が成功したケース数 |
| `measured_trials` | 成功した試行数 |
| `total_trials` | 実行した試行総数（エラー含む） |
| `trial_coverage` | `measured_trials / total_trials` |

`case_coverage` と `trial_coverage` を区別すること。3 試行中 1 試行のみ成功したケースは、ケースとしては測定済みだが代表値の信頼性は低い。この差はスコアの解釈に影響する。

### 2.2 レポートへの表示

#### 要件

- カテゴリ別評価マトリクスの**全セルにカバレッジを併記**する。
- 表示形式を以下に統一する。

```
<代表値スコア> (満点 <fully_passed>/<measured_cases>, 測定 <measured_cases>/<total_cases>)
```

現在の `91.1% (4/10)` という表記は、分母が `total_cases` であるかのように読めるため**誤解を招く**。実際には 6 ケースの平均である。修正後は以下のようになる。

```
91.1% (満点 4/6, 測定 6/10)
```

- `case_coverage` が 100% 未満のセルには警告マーク（`⚠️`）を付与する。
- レポート冒頭の実行条件サマリに、**モデル別・カテゴリ別のカバレッジ表**を独立して掲載する。
- 全試行がエラーとなったケースは、`unmeasured_cases` として case_id・モデル・エラー種別とともに一覧表示する。

### 2.3 現行の注記処理の修正

現在、レポート第 2 章に「母数が 5 未満のセルには注意マークが付与されています」という注記が、**該当セルが存在しない場合でも無条件で出力**されている。

- 該当するセルが 1 つ以上存在する場合にのみ注記を出力するよう修正する。
- 同様に、カバレッジ警告の注記も該当セルがある場合にのみ出力する。

条件に関わらず表示される注記は、読み手が注記全般を無視するようになる原因となる。

## 3. 比較可能性の保証

### 3.1 問題

モデル間でカバレッジが異なる場合、各モデルのスコアは**異なるケース集合に対する平均値**となる。これを同一の表に並べて比較することは、追補 v1 で禁止したマージガード違反と同種の問題である。

初回実測では、`gemini-3.7-flash` は 6 ケース、他 2 モデルは 10 ケースの平均が、同一行に並べられていた。

### 3.2 要件

- カテゴリ別マトリクスに加えて、**共通測定ケースのみに絞った比較表**を出力する。
  - 対象は、比較対象の全モデルで少なくとも 1 試行が成功したケースに限る
  - この表を `common_case_matrix` として `eval_raw_*.json` に格納し、レポートにも掲載する
  - 表の見出しに、対象ケース数と除外されたケース数を明記する
- **モデル間の優劣を論じる際は `common_case_matrix` を参照する**旨を、レポートおよび仕様書に明記する。
- 全モデルのカバレッジが 100% である場合、両表は一致する。その場合は重複掲載を避け、その旨を注記してよい。

### 3.3 マージガードへの追加

`eval/guard.py` に以下の検証を追加する。

- 単一の比較表に含まれるモデル間で `case_coverage` が異なる場合、**警告を発する**。
- ただし追補 v1 の 4 項目（`provider_route` 等）とは異なり、これは例外送出ではなく警告とする。カバレッジ差のある表も、カバレッジが明示されていれば掲載する価値があるため。
- 警告内容はレポートに出力し、生データにも `coverage_warnings` として記録する。

## 4. 失敗の分布に関する指標

### 4.1 背景

初回実測において、以下の対比が観測された。

| モデル | カテゴリ | 代表値 | 満点ケース |
| :--- | :--- | :---: | :---: |
| `gemini-3.5-flash-lite` | `negative_constraint` | 88.3% | 8/10 |
| `gemini-3.7-flash` | `negative_constraint` | 91.1% | 4/6 |

平均スコアが近い、あるいは逆順であっても、**失敗の分布は大きく異なりうる**。

- 「少数のケースで大きく失敗し、他は完璧」（集中型）
- 「多数のケースで小さく失敗する」（分散型）

この2つは平均値では区別できないが、運用上の意味は大きく異なる。集中型は失敗ケースを特定して個別対処できるのに対し、分散型は原因の切り分けが困難である。

### 4.2 要件

ケーススコアの分布を表す指標を集計に追加する。

| 指標 | 定義 |
| :--- | :--- |
| `perfect_case_ratio` | スコア 1.0 のケース数 / 測定ケース数 |
| `zero_case_ratio` | スコア 0.0 のケース数 / 測定ケース数 |
| `score_stddev` | ケーススコアの標準偏差 |

- これらをカテゴリ別・モデル別に算出し、生データおよびレポートに出力する。
- レポートには、代表値スコアとは**別のセクション**として「失敗分布」を掲載する。マトリクスのセルに詰め込むと可読性が損なわれるため。
- `score_stddev` が大きいモデル・カテゴリの組を、`concentrated_failures` として一覧化する。

## 5. 考察レポートの生成制約

### 5.1 問題

`eval/aggregator.py` が生成する `eval_report_latest.md` は、追補 v1 の制約（断定的な推奨の禁止）を遵守している。

一方、`eval_matrix_analysis.md`（考察レポート）には以下の違反がある。

- 「運用上の推奨モデル選定」として、用途別の推奨モデルを断定的に提示している
- 「コスト対効果が圧倒的に優れる」等の主観的評価表現を含む
- **測定データに存在しない外部情報**（トークン単価 `$0.075/1M in`）を根拠として引用している
- 欠測により算出された 91.1% を、モデルの能力（「抑制力が高い」）として解釈している

### 5.2 要件

考察レポートの生成に、以下の制約を適用する。

- **測定データに含まれない数値・事実を記載してはならない**。価格、モデルの仕様、他所での評価結果などの外部情報を持ち込まない。
- 断定的な推奨（「〜が最適」「〜を推奨」「〜が優れる」）を生成しない。事実の記述と、観測された差分の指摘に留める。
- スコアに言及する際は、**必ずカバレッジを併記**する。
- エラーによる欠測がある場合、そのスコアをモデルの能力として解釈してはならない。「測定できていない」という事実を記述する。
- 上記制約を、考察レポート生成時のプロンプトまたはテンプレートに明示的に組み込むこと。

### 5.3 検証

生成された考察レポートに対し、以下を機械的に検証する仕組みを設けることが望ましい。

- 禁止表現リスト（「推奨」「最適」「優れる」等）との照合
- レポート内に出現する数値が、生データに存在する値と対応しているかの確認

完全な検証は困難であるため、初期実装では禁止表現の検出と警告出力までとしてよい。

## 6. seed の有効性確認

### 6.1 問題

初回実測において、`gemini-3.1-pro-preview` の以下のケースで試行間スコアが大きく振れている。

| Case ID | 最小 | 最大 |
| :--- | :---: | :---: |
| `neg_05` | 0% | 100% |
| `neg_06` | 50% | 100% |
| `reasoning_01` | 0% | 100% |

`temperature=0.0`, `seed=42` を指定しているため、本来この振れ幅は想定されない。

### 6.2 調査手順

1. `generation_config` に指定した `seed` が、実際に API リクエストに含まれているかを確認する。
2. 対象モデル（特に preview 版）が `seed` パラメータをサポートしているかを確認する。
3. API レスポンスに、指定したパラメータが受理されたことを示す情報が含まれるか確認する。
4. 同一ケース・同一モデルで 5 回程度の追加試行を行い、出力の生テキストが一致するかを確認する。

### 6.3 対応

| 調査結果 | 対応 |
| :--- | :--- |
| `seed` が送信されていない実装バグ | 修正する |
| モデルが `seed` 非対応 | 仕様書 5.1 の注記を更新し、当該モデルでは再現性が保証されない旨を明記。試行回数の増加を検討する |
| `seed` 送信済みだが出力が揺れる | 仕様書に既知の制約として記録し、`unstable_cases` の検出をもって対処とする |

**調査結果を必ず報告すること。** 結果に関わらず、判明した事実を仕様書 5.1 に反映する。

## 7. Phase 1 完了条件の再検証

追補 v1 で定義した Phase 1 の完了条件のうち、以下は**未検証**である。

> 同一条件で 2 回実行し、代表値が一致すること（再現性の確認）

初回実測は 1 回のみである。本追補の 1〜6 の対応完了後、以下を実施すること。

- 同一条件で 2 回実行する
- 2 回の `category_matrix` および `common_case_matrix` を比較する
- 一致しない場合、差異が生じたケースを特定して報告する
- 両実行の `run_id`、カバレッジ、エラー件数を併記した比較結果を出力する

**この検証が通るまで、測定結果を外部に提示できる品質とはみなさない。**
