# 📗 SPECIFICATION 追補 — 評価基盤の再設計 (ADDENDUM v1)

本ドキュメントは `docs/SPECIFICATION.md` に対する**追補仕様**である。既存仕様と矛盾する箇所は本追補を優先する。実装完了後、本追補の内容を `docs/SPECIFICATION.md` 本体へマージし、本ファイルは削除してよい。

## 実装の全体方針

現行の評価基盤は「固定データセットを毎回実行する golden dataset 型」である。これは維持する。そのうえで、**本番トラフィックを蓄積し、後から任意の候補モデルでリプレイする基盤**を第二の系統として追加する。

2系統の役割は次のとおり。混同しないこと。

| 系統 | 目的 | 入力 | 実行頻度 |
| :--- | :--- | :--- | :--- |
| Golden dataset（既存） | 現行構成の劣化検知 | コード/テーブル上の固定ケース | デプロイ時・日次 |
| リプレイ評価（新規） | 候補モデルへの切り替え判断 | 蓄積された実トラフィック | 検討期間のみ随時 |

**実装優先順位は Phase 1 → 2 → 3 とする。Phase 1 が完了するまで Phase 2 以降に着手しないこと。** Phase 1 は既存の測定結果の信頼性に直結する修正であり、ここが未完了のまま件数やモデルを増やしても数値は解釈できない。

# Phase 1: 測定の信頼性確保（最優先）

現行実装では、測定値がモデルの性能差を反映しているとは言えない。以下を修正する。

## 1.1 生成パラメータの固定

### 問題
採点ロジックは決定論的だが、生成側の温度設定が仕様上未定義であり、実装でも明示されていない。1回きりの実行では、生成のゆらぎがそのままモデル間の差として観測される。

### 要件

- 評価実行時のモデル呼び出しは、以下を明示的に指定すること。
  - `temperature = 0.0`
  - `top_p`, `top_k` は指定せず、モデル既定に委ねる（指定する場合は結果メタデータに記録すること）
  - `max_output_tokens` はケースごとに固定値を設定し、データセット定義に含めること
- `seed` パラメータをサポートするモデルでは固定値を指定し、記録すること。非対応の場合はメタデータに `seed: null` と記録する。

## 1.2 複数試行と代表値の採用

### 要件

- 各 (ケース, モデル) の組に対して **N回試行**する。既定は `N = 3`。
- 環境変数 `EVAL_TRIALS`（既定 `3`）で変更可能にする。
- 試行結果は**すべて個別に永続化**する。集計時に平均するのではなく、生データとして全試行を保持すること。
- 代表値は**中央値**を採用する。平均は外れ値に引きずられるため使用しない。
- 集計出力には代表値に加えて**試行間のばらつき**（最小値・最大値、または標準偏差）を必ず含める。

### 判定基準への反映

試行間でスコアが割れたケースは、モデル性能ではなく**ケース設計の不備**を示唆する。集計レポートに「試行間で結果が不安定なケース」の一覧を出力すること。

## 1.3 フォールバック機構の評価時無効化

### 問題
`ChatAgentManager` は ADK 実行に失敗すると google-genai SDK 直呼びへフォールバックする。チャット機能としては正しい設計だが、評価実行時にこれが発動すると、ADK 経由の結果と SDK 直呼びの結果が同一の集計表に混在する。かつ、どちらの経路で実行されたかが結果に残らない。

### 要件

- `ChatAgentManager` に**フォールバック無効モード**を追加する。
  - コンストラクタ引数または実行時フラグで制御する（例: `allow_fallback: bool = True`）
  - 評価ランナーからの呼び出しでは必ず `allow_fallback=False` を指定する
- フォールバック無効モードでは、ADK 実行の失敗を例外としてそのまま伝播させる。
- 評価ランナーは失敗を**失敗として記録**する。スコア 0 として集計に混ぜてはならない。失敗は成功ケースとは別の集計軸で扱う。
- 実際に使用された実行経路（`adk` / `genai_sdk_fallback`）を、フォールバックを許可した場合は必ず結果メタデータに記録する。

## 1.4 実行メタデータの記録

### 問題
現行の出力スキーマにはモデル名は含まれるが、実行環境を識別する情報が欠けている。このため、異なる実行経路・異なる設定で得られた結果を、集計時に区別できない。過去に Vertex AI 経由の実行結果と AI Studio 経由の実行結果が単一のマトリクスに統合され、比較として成立しない表が生成された。

### 要件

各試行レコードに以下のフィールドを必ず含めること。

| フィールド | 型 | 説明 |
| :--- | :--- | :--- |
| `run_id` | string | 実行単位の一意識別子（UUID または タイムスタンプベース） |
| `trial_index` | int | 同一 (ケース, モデル) 内での試行番号 (0-origin) |
| `case_id` | string | 評価ケースの識別子 |
| `category` | string | 評価カテゴリ |
| `model_id` | string | モデル識別子。**完全なバージョン文字列**を使用すること（1.5 参照） |
| `provider_route` | enum | `vertex_ai` / `ai_studio` |
| `location` | string | Vertex AI のリージョン。AI Studio の場合は `null` |
| `execution_path` | enum | `adk` / `genai_sdk_fallback` |
| `instruction_hash` | string | システムインストラクション文字列の SHA-256 先頭 12 文字 |
| `dataset_version` | string | 評価データセットのバージョン識別子 |
| `evaluator_version` | string | 採点ロジックのバージョン識別子 |
| `sdk_versions` | object | `google-adk` および `google-genai` のインストール済みバージョン |
| `generation_config` | object | temperature, seed, max_output_tokens などの実際の指定値 |
| `status` | enum | `success` / `error` |
| `error_type` | string | 失敗時のエラー種別（HTTP ステータス、例外クラス名など）。成功時は `null` |
| `latency_ms` | int | 実行に要した時間 |
| `score` | float | 採点結果。`status=error` の場合は `null`（0 ではない） |
| `raw_output` | string | モデルの生出力。デバッグと事後検証のため必ず保存する |

`instruction_hash`, `dataset_version`, `evaluator_version` の3つは、**プロンプトや採点ロジックの変更をまたいだ比較を防ぐ**ために必須である。

## 1.5 モデル識別子の厳密化

### 要件

- 評価対象のモデルは、**エイリアスではなく完全なバージョン文字列**で指定すること。
- 実行開始前に、指定されたモデル識別子が**対象の実行経路で解決可能か**を検証する事前チェックを実装する。
  - 各モデルに対して最小のリクエストを1回投げ、成功を確認してから本実行に入る
  - 解決できないモデルは、その旨を明示してスキップし、結果テーブルに 0% の行を作らない
- 事前チェックの結果は実行ログに出力し、レポート冒頭に「評価対象として有効だったモデル」の一覧を掲載する。

## 1.6 集計時のマージガード

### 問題
集計レポートの自動生成において、比較不能な結果が単一の表に統合された実績がある。

### 要件

集計処理に以下のバリデーションを実装し、違反時は**例外を送出して集計を中断**する。単なる警告ではなく中断とすること。

- 単一の比較表に含まれるレコードは、以下がすべて一致していなければならない。
  - `provider_route`
  - `instruction_hash`
  - `dataset_version`
  - `evaluator_version`
- 上記が異なるレコードを比較したい場合は、**表を分割**する。分割した表には、どの条件が異なるかを明示する見出しを付ける。
- 複数の `run_id` の統合は許可するが、上記4項目が一致する場合に限る。統合した場合はレポートに統合元の `run_id` をすべて列挙する。

## 1.7 集計レポートの記述制約

自動生成されるレポートは、以下の制約に従うこと。

- **サンプル数を必ず併記**する。`50.0%` ではなく `50.0% (1/2)` の形式で出力する。
- 母数が 5 未満のセルには注意マークを付与し、レポート末尾に「サンプル数が少なく差を有意と解釈できない」旨の注記を出力する。
- モデルの優劣に関する断定的な推奨文（「〜が最適」「〜を推奨」）を生成しない。事実の記述と、確認された差分の指摘に留めること。解釈は人間が行う。
- レポート冒頭に**実行条件のサマリ**（実行経路、リージョン、試行回数、temperature、データセットバージョン、評価対象モデル一覧）を必ず出力する。

# Phase 2: 評価データセットの拡充と外部化

## 2.1 カテゴリの絞り込みと件数増強

### 問題
現行は全13ケースを5カテゴリに分散させており、カテゴリあたり2〜3ケースである。この母数ではカテゴリ別スコアの差を解釈できない。

### 要件

- カテゴリを **3つに絞る**。採用するのは以下。
  - `structured_output`
  - `negative_constraint`
  - `multi_step_reasoning`
- 各カテゴリ **最低10ケース**、合計30ケース以上とする。
- 除外する `long_context_retrieval` と `ambiguous_intent` のケースは削除せず、データセット内で `enabled: false` として保持する。将来的に件数を確保できた時点で復活させる。

### カテゴリ内の難易度傾斜

各カテゴリ内で、判定の厳しさに段階を設けること。全ケースが同難易度だと、モデル間の差が出るか出ないかの二値になり、内訳の情報量が失われる。

- 例（`structured_output`）: 単純なフラット JSON / ネストした構造 / 配列を含む構造 / 出力形式の付帯制約（コードブロックで囲まない等）を組み合わせる
- 各ケースに `difficulty` フィールド（`basic` / `intermediate` / `advanced`）を付与し、集計軸として使用可能にする

## 2.2 採点の粒度

### 要件

- 1ケースの採点結果を単一のスコアに丸めず、**アサーション単位の合否**を記録する。
  - 例: JSON としてパース可能か / スキーマに適合するか / コードブロックで囲まれていないか、を独立した判定として保持する
- ケーススコアは、アサーションの合格数 / 総アサーション数として算出する。
- 集計レポートで**アサーション単位の失敗内訳**を出力する。どの制約で落ちているかが分かることが、この評価基盤の主要な価値である。

この粒度が、カテゴリ平均だけでは見えない失敗パターンを可視化する。

## 2.3 データセットのテーブル化

### 要件

- 評価データセットの定義を `dataset.py` のコード内リテラルから、**外部データとして分離**する。
- 段階的に実施してよい。
  - 第一段階: JSON / YAML ファイルとして `eval/datasets/` 配下に切り出す。`dataset.py` はローダーに徹する
  - 第二段階: BigQuery テーブルへ移行する（Phase 3 と合わせて実施）
- データセットには `dataset_version` を持たせ、変更時に更新する。バージョンは 1.4 のメタデータに記録される。

分離の理由は、評価ケースの追加がエンジニア以外にも可能であるべきこと、および追加のたびにデプロイを要求すると評価セットが更新されなくなることによる。

# Phase 3: 蓄積とリプレイの基盤

Phase 1・2 が golden dataset 系統の改善であるのに対し、本フェーズは**第二の系統を新設**するものである。

## 3.1 本番トラフィックの構造化ログ蓄積

### 問題
`/api/chat` の入出力はどこにも永続化されていない。セッション状態も `InMemorySessionService` により揮発する。リプレイ評価は蓄積されたトラフィックを前提とするため、蓄積を先に開始しないと後から遡って取得することはできない。

### 要件

- `/api/chat` の処理において、リクエストとレスポンスを構造化ログとして永続化する。
- 出力先は環境変数で切り替え可能にする。
  - `EVAL_LOG_SINK=jsonl`: ローカルの JSONL ファイル（開発時の既定）
  - `EVAL_LOG_SINK=bigquery`: BigQuery テーブル
  - `EVAL_LOG_SINK=none`: 無効
- 永続化は**非同期・ベストエフォート**とする。ログ書き込みの失敗がチャット応答をブロックしてはならない。失敗時はエラーログに記録して処理を継続する。

### 蓄積スキーマ

| フィールド | 型 | 説明 |
| :--- | :--- | :--- |
| `query_id` | string | 一意識別子 |
| `timestamp` | timestamp | 受信時刻 |
| `session_id` | string | セッション識別子 |
| `input_text` | string | ユーザー入力 |
| `conversation_context` | array | リプレイに必要な直前までの会話履歴 |
| `output_text` | string | 実際に返した応答 |
| `model_id` | string | 応答生成に使用したモデル（完全バージョン文字列） |
| `provider_route` | enum | `vertex_ai` / `ai_studio` |
| `instruction_hash` | string | その時点のシステムインストラクションのハッシュ |
| `generation_config` | object | 実際の生成パラメータ |
| `latency_ms` | int | 応答時間 |

`conversation_context` は必須である。マルチターンの会話では、入力単体をリプレイしても本番と同じ状況を再現できない。

### 個人情報の扱い

蓄積対象にユーザー入力が含まれるため、以下を実装すること。

- ログ保存前のマスキング処理を挟める構造にする（初期実装は素通しでよいが、フックを設ける）
- 保持期間の設定を可能にする（BigQuery の場合はテーブルのパーティション有効期限）
- 蓄積が有効であることを設定ファイルおよび README に明記する

## 3.2 リプレイ実行ジョブ

### 要件

- 蓄積されたクエリに対し、指定した候補モデルで応答を再生成するジョブを実装する。
- 入力は「蓄積テーブルからの抽出条件」（期間、件数上限、サンプリング方法）で指定する。
- **バッチ推論を使用する**。オンライン推論のループで実装してはならない。
  - Vertex AI のバッチ推論機能を用いる
  - 実装前に、対象モデルがバッチ推論に対応しているかを確認すること
  - 対応していない場合は、その事実を記録したうえでオンライン実行にフォールバックしてよいが、その旨を結果メタデータに明示する
- リプレイ結果は、**Phase 1.4 と同一のスキーマ**で永続化する。golden dataset の評価結果と同じテーブル構造に格納し、`source` フィールド（`golden_dataset` / `replay`）で区別する。

### 候補の複数指定

- 1回のジョブ実行で **N個の候補**を指定できること。候補は「モデル」に限らず、以下の組み合わせで定義される。
  - モデル識別子
  - システムインストラクション
  - 生成パラメータ
- 候補を `candidate_id` で識別し、結果レコードに含める。これにより、モデル比較・プロンプト比較・パラメータ比較を同一の基盤で扱える。

### コストと所要時間の記録

- ジョブ実行ごとに、処理件数・入出力トークン数・所要時間を記録する。
- これらは基盤の運用コストを把握するための必須情報である。

## 3.3 差分分析

### 要件

- 蓄積された評価結果に対し、候補間の差分を算出する処理を実装する。
- 算出軸は最低限以下を含む。
  - 候補 × カテゴリ
  - 候補 × アサーション種別
  - 候補 × difficulty
- リプレイ評価では正解ラベルが存在しないケースが多いため、**決定論的に判定可能な観点に限定**する。
  - 出力形式の妥当性（JSON パース可否、スキーマ適合）
  - 禁止表現の混入有無
  - 出力長の分布
  - 現行モデルの出力との差異の大きさ（完全一致率、編集距離など）
- LLM-as-a-judge は**導入しない**。判定側の不確実性が候補間の差と混ざり、差分の原因を切り分けられなくなるため。

# 実装上の禁止事項

以下は明示的に行わないこと。

- 採点ロジックへの LLM-as-a-judge の導入
- 異なる `provider_route` / `instruction_hash` / `dataset_version` / `evaluator_version` の結果を単一の比較表に統合すること
- 失敗（エラー）をスコア 0 として成功ケースと同じ集計に混ぜること
- 評価実行時のフォールバック機構の有効化
- モデル識別子のエイリアス指定
- 集計レポートにおける、サンプル数を伴わないパーセンテージ表記
- 自動生成レポートにおけるモデル推奨の断定
