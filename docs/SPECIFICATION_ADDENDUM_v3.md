## 1. ADK Runner の実行方式

### 現状

`SPECIFICATION.md` 3.4 の記述が、以前の版の `Runner.run_async` から `Runner.run` に変更されている。

バックエンドは FastAPI の非同期エンドポイント（`async def`）として実装されている。この文脈で同期版の `Runner.run` を呼び出している場合、**イベントループを占有し、他のリクエストの処理をブロックする**可能性がある。

単一ユーザーでの開発時には顕在化しないが、以下の状況で影響が出る。

- 複数ユーザーが同時にチャットを利用する場合
- 1リクエストの応答生成に時間がかかるモデルを使用する場合
- 評価実行とチャットを並行させる場合

### 調査手順

1. `backend/agent.py` の `ChatAgentManager` において、実際に呼び出しているメソッドを確認する。
2. そのメソッドが同期関数か非同期関数かを確認する。
3. 同期関数である場合、呼び出し元が `async def` の中で直接 `await` なしに呼んでいるか、`run_in_executor` / `asyncio.to_thread` 等でスレッドに逃がしているかを確認する。
4. `google-adk` の当該バージョンにおいて、非同期版のメソッドが提供されているかを確認する。

### 対応方針

調査結果に応じて分岐する。**どのケースに該当したかを必ず報告すること**。

| 調査結果 | 対応 |
| :--- | :--- |
| 非同期メソッドを使用している（仕様書の記述が誤り） | 仕様書 3.4 の記述を実装に合わせて修正する |
| 同期メソッドだが、スレッドプールに逃がしている | 仕様書 3.4 にその旨を明記する。ブロッキング回避の実装であることが読み取れる記述にする |
| 同期メソッドをイベントループ上で直接呼んでいる | 修正が必要。下記「修正時の要件」に従う |
| ADK が非同期版を提供していないため同期呼び出しが不可避 | 仕様書 3.4 に制約として明記する。「既知の制約」として、同時実行時にブロッキングが発生しうることを記載する |

### 修正時の要件

同期メソッドをイベントループ上で直接呼んでいた場合のみ、以下を実施する。

- 非同期版のメソッドが利用可能であればそちらへ切り替える。
- 非同期版が存在しない場合は、`asyncio.to_thread` 等でスレッドへ委譲する。
- 変更は `/api/chat` の外部仕様（リクエスト・レスポンスの形式）を変えないこと。
- 開発ルールに従い TDD で実施する。同時に複数リクエストを投げてブロッキングが発生しないことを確認するテストを追加すること。
- フォールバック機構および `allow_fallback=False` の挙動に影響を与えないこと。

## 2. JSON 妥当性率と CodeBlock 混入率の関係

### 現状

`SPECIFICATION.md` 6.4（決定論的差分分析）に、2つの近接した指標が定義されている。

- **JSON 妥当性率**: 「出力から Markdown を除いたテキストが JSON 構文として有効である割合」
- **CodeBlock 混入率**: 「Markdown バッククォート (```) の混入割合」

前者が Markdown を除去してから判定する仕様であれば、**この2指標は独立した観点を測っている**。すなわち、

- JSON 妥当性率 = 中身の構造が正しいか
- CodeBlock 混入率 = 出力形式の指示に従えているか

出力が ` ```json {...} ``` ` の形をとる場合、JSON 妥当性率は合格、CodeBlock 混入率のみ不合格となる。

### 確認が必要な理由

この設計は**意図的であれば正しい**。中身の正しさと形式の遵守を分離して観測できるため、「構造は理解しているが出力形式の指示に従えていない」という失敗パターンを識別できる。これは実際にベンチマークで観測された挙動である。

一方、Markdown 除去が「判定を通しやすくするための前処理」として無自覚に入っている場合、形式違反が JSON 妥当性率から見えなくなり、指標の意味が曖昧になる。

### 調査手順

1. `backend/eval/traffic/diff_analyzer.py` における JSON 妥当性判定の実装を確認する。
2. Markdown 除去処理が入っているか、入っている場合その対象（コードブロックのみか、他の Markdown 記法も含むか）を確認する。
3. `backend/eval/evaluator.py` の `structured_output` カテゴリの採点ロジックと**判定方針が一致しているか**を確認する。両者で扱いが異なる場合、同じ出力に対して異なる評価結果が出ることになる。

### 対応方針

| 調査結果 | 対応 |
| :--- | :--- |
| 2指標が独立した観点として設計されている | 仕様書 6.4 にその設計意図を明記する（下記参照） |
| Markdown 除去が前処理として無自覚に入っている | 指標の定義を見直し、意図を確定させたうえで仕様書に反映する |
| `evaluator.py` と `diff_analyzer.py` で判定方針が異なる | 差異を報告する。統一するか、意図的な差異として明記するかを判断できる形で提示すること |

### 仕様書への追記内容

2指標が独立設計である場合、6.4 に以下の趣旨を追記する。

> **JSON 妥当性率と CodeBlock 混入率は、意図的に独立した観点として定義されている。**
> 前者は出力の構造的な正しさを、後者は出力形式に関する指示の遵守を測る。
> コードブロックで囲まれた有効な JSON は、JSON 妥当性率では合格、CodeBlock 混入率では不合格として計上される。
> この分離により、「構造は正しく生成できているが、形式指示に追従できていない」という失敗パターンを識別できる。
