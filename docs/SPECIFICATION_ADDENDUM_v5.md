# 📗 SPECIFICATION 追補 — 打ち切り原因の特定と不良ケースの検出 (ADDENDUM v5)

本ドキュメントは `docs/SPECIFICATION.md` に対する**追補仕様（第5版）**である。

追補 v4 の対応により、レート制限による欠測は解消され、カバレッジ 100% の測定が達成された（`run_id: 20260830_175501`）。本追補は、その測定結果を分析する過程で判明した**測定の妥当性に関わる未解決事項**を扱う。

## 本追補の起点となった問題

`gemini-3.5-flash-lite` が上位モデル（`gemini-3.7-flash`, `gemini-3.1-pro-preview`）を総合スコアで上回るという結果に対し、これまで3つの説明が提示された。

| 回 | 提示された説明 | 検証結果 |
| :--- | :--- | :--- |
| 1 | 問題設定が簡単すぎる（天井効果） | 満点は 30 ケース中 18 件。0 点も存在し、天井効果では説明できない |
| 2 | 高性能モデルは過剰に親切で、機械的制約に不適合 | 提示された3例のうち2例が事実誤認。1例（`struct_09`）のみ成立 |
| 3 | 思考モデルが `max_output_tokens` を内部推論で消費している | 数値は正確だが、**原因の特定に必要なデータが記録されていない** |

**測定された数値は一度も変わっていない。変わったのは解釈だけである。**

現状、以下が判明している。

- `gemini-3.7-flash` は 30 ケース中 15 件、`gemini-3.1-pro-preview` は 17 件で可視出力が 50 トークン以下（`gemini-3.5-flash-lite` は 4 件）
- `max_output_tokens=1024` に対する可視出力の平均利用率は 7.9% / 7.5% / 24.8%
- `reasoning_05` などで、出力が文の途中で終わっている（`犯人以外の2` で停止）

しかし**なぜ停止したのかを判定するデータが存在しない**。現行のレコードには `prompt_tokens` と `candidate_tokens` のみが記録されており、停止理由も思考トークン数も残っていない。

したがって「思考トークンが出力枠を圧迫している」という説明は、観測された空白からの推論であり、検証されていない。以下の代替説明も同様に否定できない。

- モデルが正常終了している（短く答える傾向を持つ）
- safety フィルタ、stop sequence その他の停止条件で終了している
- プロンプトの解釈に失敗して指示を復唱している（`gemini-3.7-flash` の `neg_03` は「`の漢字などを使わずカタカナに直す。`」という指示の言い換えを出力しており、思考枠の問題では説明できない）

**本追補の目的は、原因を特定できる状態にすることである。対処ではない。** `max_output_tokens` の変更や `thinking_config` の設定は、原因が確定した後に行う。

## 1. 停止理由の記録（最優先）

### 1.1 問題

出力が文の途中で終わっているように見えても、それが以下のどちらであるかを現状のデータでは判別できない。

- トークン上限に達して打ち切られた
- モデルが正常に応答を終了した

この判別ができない限り、`max_output_tokens` を変更しても改善したかどうかを確認できない。

### 1.2 要件

各試行レコードに以下のフィールドを追加する。

| フィールド | 型 | 説明 |
| :--- | :--- | :--- |
| `finish_reason` | string | API が返す停止理由（`STOP`, `MAX_TOKENS`, `SAFETY` 等）を原文のまま記録 |
| `truncated` | bool | `finish_reason` がトークン上限による打ち切りを示す場合 `true` |

- `finish_reason` は**加工せずに記録する**。SDK が enum を返す場合はその文字列表現を格納する。
- 値が取得できない場合は `null` を格納し、その旨を集計レポートに明示する。推測値を入れてはならない。
- `truncated` の判定条件（どの `finish_reason` を打ち切りとみなすか）を実装内にコメントで明記する。

### 1.3 集計への反映

- モデル別・カテゴリ別の `truncation_rate`（`truncated=true` の試行数 / 総試行数）を算出する。
- レポートに独立したセクションとして「打ち切り率」を掲載する。
- `truncation_rate` が 0% でないモデル・カテゴリの組には警告マークを付与する。
- 打ち切りが発生した試行を含むケースは、**スコアの解釈に注意が必要**である旨をレポートに注記する。

### 1.4 スコア解釈への影響

打ち切られた試行のスコアは、モデルの能力を反映していない可能性がある。

- 打ち切られた試行を、追補 v1 のエラー（`status=error`）と同様に扱うべきかは**判断を保留する**。本追補では記録と可視化までとし、集計方法の変更は行わない。
- ただし考察レポートにおいて、`truncated=true` の試行を含むスコアをモデルの能力として解釈してはならない。

## 2. 思考トークンの記録

### 2.1 問題

「内部推論が出力予算を消費している」という説明の検証には、思考トークン数の実測が必要である。現行のレコードにこのフィールドは存在しない。

### 2.2 要件

- 使用している SDK（`google-genai`）のレスポンスに、思考トークン数を示すフィールド（`thoughts_token_count` 相当）が含まれているかを確認する。
- 含まれている場合、レコードに `thinking_tokens` として記録する。
- 含まれていない場合、または対象モデルで値が返らない場合は `null` を記録し、**「思考トークン数は測定不能」であることを仕様書に明記する**。
- レスポンスの `usage_metadata` 相当の情報全体を `usage_raw` として保存することを推奨する。将来的に必要になるフィールドを予測できないため。

### 2.3 検証と報告

思考トークンが記録できた場合、以下を報告すること。

- モデル別の `thinking_tokens` の分布（中央値、最大値）
- `thinking_tokens + candidate_tokens` が `max_output_tokens` に達しているケースの件数
- 上記が `truncated=true` のケースと一致しているか

**記録できなかった場合は、「思考トークンが原因である」という説明を仕様書・レポート・考察のいずれにも記載してはならない。** 検証不能な仮説として扱う。

## 3. 全モデル同点ケースの精査

### 3.1 問題

30 ケースのうち 22 ケースで 3 モデルの代表値が一致している。うち 18 ケースは全モデル満点であり、これは正常な結果である。

しかし残り 4 ケースは同点かつ満点未満である。

| Case ID | 3モデル共通の代表値 |
| :--- | :---: |
| `struct_02` | 0.875 |
| `struct_06` | 0.8 |
| `reasoning_01` | **0.0** |
| `reasoning_03` | **0.0** |

**`reasoning_01` と `reasoning_03` は全モデルが 0 点である。** 3モデル・3試行のすべてが 0 点となる場合、モデルの能力差ではなくケース自身に問題がある可能性が高い。

想定される原因は以下。

- 期待値（アサーション）の設定が誤っている
- 正解が一意に定まらない問題文になっている
- アサーションの正規表現が、正しい回答でもマッチしない
- 問題文自体に矛盾がある

`reasoning_01` は追補 v4 の `unstable_cases` にも `gemini-3.1-pro-preview` で 0%〜100% として挙がっており、判定が安定していない。

### 3.2 要件

- 上記4ケースについて、**問題文・期待値・全モデルの生出力を突き合わせて精査する**。
- 精査結果を以下のいずれかに分類し、報告すること。
  - ケース設計の不備（アサーションまたは問題文が誤っている）
  - 全モデルが実際に解けない高難度ケース（正当な結果）
  - 判定不能（さらなる調査が必要）
- **ケース設計の不備と判定された場合のみ**、ケースを修正するか `enabled: false` として無効化する。修正時は `dataset_version` を更新する。
- 正当な高難度ケースであった場合は、そのまま維持する。全モデルが失敗するケースを除外すると、評価セットが易化する方向に偏るため。

### 3.3 恒常的な検出機構

同種の問題を今後自動的に検出するため、以下を集計に追加する。

- **`all_models_zero_cases`**: 全モデルの代表値が 0.0 のケース一覧
- **`all_models_tied_imperfect_cases`**: 全モデルの代表値が一致し、かつ 1.0 未満のケース一覧

これらをレポートに「ケース設計の精査候補」として出力する。モデルを評価する指標ではなく、**評価セット自身を評価する指標**である。

## 4. 考察レポートの検証可能性

### 4.1 問題

追補 v4 §5 で考察レポートの生成制約を定めたが、以下2点が未対応である。

- `eval_matrix_analysis.md` に「運用上の推奨モデル選定」が残存し、断定的な推奨が記載されている
- 測定データに存在しない外部情報（トークン単価 `$0.075/1M in`）が根拠として引用されている

加えて、これまでに生成された考察には**事実誤認**が含まれていた。具体例として、`neg_03` において `gemini-3.1-pro-preview` は満点（1.0）であるにもかかわらず「不合格」と記述されていた。

代表例を数件見て一般化する方式では、こうした誤りが生じる。

### 4.2 要件：考察生成前の機械的集計

考察を記述する前に、以下の集計を機械的に実行し、**その出力を考察の根拠として参照する**構造にする。

- **失敗原因の分類集計**: 各失敗アサーションを以下に分類し、モデル別・分類別の件数を出力する。
  - `truncated`: 打ち切りにより回答が完成していない
  - `instruction_not_followed`: タスクを実行せず、指示の復唱や無関係な出力を返している
  - `over_specified`: 期待値に余分な情報を付加している（例: `"HND (東京羽田)"`）
  - `incorrect`: 回答は完成しているが内容が誤っている
- 分類は可能な範囲で機械判定し、判定できないものは `unclassified` とする。**推測で分類してはならない。**
- 分類結果を `failure_classification` として生データおよびレポートに出力する。

### 4.3 要件：考察の記述制約

追補 v4 §5.2 の制約を再掲し、加えて以下を課す。

- 考察において個別ケースを例示する場合、**そのケースの全モデルのスコアを併記する**。1モデルのみに言及して他を省略してはならない。
- 「〜と考えられる」「〜の可能性が高い」といった推論を記述する場合、**それが推論であることを明示**し、検証に必要なデータが存在するかを述べる。存在しない場合は「現データでは検証不能」と記載する。
- 断定形で書けるのは、生データから直接確認できる事実に限る。

### 4.4 要件：v4 §5 の未対応分の実施

- `eval_matrix_analysis.md` から「運用上の推奨モデル選定」セクションを削除する。
- 外部情報（価格等）の記載を削除する。
- スコア表記を自動生成レポートと同一形式（`<スコア> (満点 x/y, 測定 y/z)`）に統一する。現在は旧形式（`94.2% (7/10)`）が残存している。
- 上記制約を、考察レポート生成時のプロンプトまたはテンプレートに**明示的に組み込む**。指示として都度与えるのではなく、生成処理に埋め込むこと。

## 5. 実施順序

**本追補の対応は以下の順序で行う。順序を変更してはならない。**

1. §1 停止理由の記録
2. §2 思考トークンの記録（可能であれば）
3. §1・§2 を含めた状態で、**同一条件（`max_output_tokens=1024` のまま）で1回再実行**
4. 打ち切り率と思考トークンの実測結果を報告
5. §3 全モデル同点ケースの精査
6. §4 考察レポートの修正

### 再実行時の条件

手順3では、**`max_output_tokens` および `thinking_config` を変更しない**。前回（`run_id: 20260830_175501`）と同一条件で実行する。

理由: 現在の目的は原因の特定であり、改善ではない。条件を変えると、前回のデータとの比較ができなくなる。打ち切りが実際に発生しているかを、まず同一条件で確認する。

### 対処の判断は本追補の範囲外

`max_output_tokens` の増加、`thinking_config` の設定（思考の無効化または予算別枠化）は、手順4の報告内容を踏まえて別途判断する。**本追補では実施しない。**

判断が分かれる論点として以下がある。実測データが揃った時点で改めて検討する。

- 思考を無効化して全モデルを同条件にするか（比較の公平性を優先）
- 思考予算を別枠で確保するか（各モデルの能力上限を測ることを優先）

前者は「API バックエンドに組み込む際の実用性」を測る設計、後者は「モデルの推論能力」を測る設計であり、**測定対象が異なる**。どちらが適切かは、この評価基盤の目的に依存する。
