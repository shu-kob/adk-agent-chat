本ドキュメントは `docs/SPECIFICATION.md` に対する**追補仕様（第6版）**である。

追補 v5 §1・§2 の対応により、`finish_reason` と `thoughts_token_count` が記録され、**打ち切りの原因が確定した**（`run_id: 20260831_070240`）。本追補は、その結果に基づく是正措置を定める。

## 確定した事実

### 思考トークンが可視出力の予算を圧迫している

`gemini-3.7-flash` / `neg_01` の実測値：

```
thoughts_token_count   : 492
candidates_token_count : 16
finish_reason          : MAX_TOKENS
可視出力               : 「自然言語処理技術の劇的な進化により、プログラミング支援や文章」（文中で停止）
```

思考に 492 トークンを消費し、可視出力は 16 トークンで打ち切られている。

打ち切りレコードにおける合計トークン（`candidates + thoughts`）の分布は 252 / 508 / 667 / 1020 に集中しており、`max_output_tokens=1024` の上限に達する前に打ち切られているケースが多い。内部的に思考予算が確保され、その分だけ可視出力の枠が削られる挙動と考えられる。

**この挙動の詳細な仕様は本追補では断定しない。** 確定しているのは「思考モデルにおいて `max_output_tokens=1024` では可視出力が成立しない」という事実である。

## 1. 思考予算の是正（案B: 予算の別枠確保）

### 1.1 方針

**可視出力の予算を思考トークンから保護する。** 思考を無効化する方針（`thinking_budget=0`）は採用しない。

採用理由：

- 思考を無効化すると、思考モデルの本来の挙動を測定できない。「思考を止めた状態のモデル」は、実際に運用するモデルとは別物である
- 「思考を殺して比較した」という測定条件は、結果の妥当性に対する新たな疑義を生む
- 現在の目的は、打ち切りという測定上の欠陥を除去して**公平な比較を成立させる**ことにある

### 1.2 要件

- `max_output_tokens` の既定値を **4096** に引き上げる。
  - 環境変数 `EVAL_MAX_OUTPUT_TOKENS`（既定 `4096`）で設定可能にする
  - データセット側でケースごとに上書きできる構造は維持する
- `thinking_config` / `ThinkingConfig` を用いて思考予算を明示的に指定できる実装を追加する。
  - 環境変数 `EVAL_THINKING_BUDGET` で設定可能にする
  - **既定値は「未設定」とする**（モデル既定の挙動に委ねる）
  - `0` を指定した場合は思考を無効化する。これは比較実験用のオプションであり、既定の測定条件としては使用しない
- `generation_config` の記録に、実際に指定した `max_output_tokens` と `thinking_budget`（未設定なら `null`）を必ず含める。

### 1.3 4096 で足りるかの検証

`4096` は暫定値である。実行後に以下を確認し、不足していれば増加させること。

- 全モデル・全カテゴリで `truncation_rate` が 0% になっているか
- 0% にならないケースについて、`candidates + thoughts` の合計が上限に達しているかを確認する
- 思考トークンの最大値は実測で 1413（`gemini-3.1-pro-preview`）であった。可視出力に十分な余裕があるかを、`candidates_token_count` の分布から判断する

**「打ち切りが減った」ではなく「打ち切りが 0 になった」を目標とする。** 1 件でも残っていれば、そのカテゴリのスコア解釈に留保が必要になる。

### 1.4 コストへの影響

`max_output_tokens` の増加自体は課金対象ではないが、実際の出力トークン数は増加する。

- 前回実行の総コストは約 `$0.059`、所要時間は約 26 分 30 秒であった
- 本追補後の実行についても、総コスト・総所要時間・モデル別トークン数を記録し、前回との比較を報告すること
- コストが数倍に増加した場合は、その事実を報告する。実行を中断する必要はない

比較表には以下を含める。

| :--- | :--- |

- この比較表を `eval_comparison_<前run_id>_vs_<新run_id>.md` として独立ファイルに出力する。
- 生データにも `comparison` として格納する。
- **`max_output_tokens` 以外の条件を変更してはならない。** temperature、seed、試行回数、データセットバージョン、システムインストラクションはすべて同一に保つ。1つの変更の効果を測るための比較であるため。

- `gemini-3.5-flash-lite` のスコアは、打ち切り率が低いため大きく変化しない見込みである。**変化しないことが期待される対照群**として扱う。

## 3. 再現性判定の見直し

### 3.1 問題

追補 v4 §7 は Phase 1 の完了条件として「同一条件で 2 回実行し、代表値が一致すること」を定めた。

しかし `gemini-3.1-pro-preview` は `seed=42` を指定しても出力が再現しない。これはモデル側の挙動であり、実装で解決できない。現行の条件では**この完了条件を永久に満たせない**。

### 3.2 要件：判定の分割

再現性の判定を、全モデル一括からモデル単位に変更する。

- 各モデルについて、同一条件 2 回実行の代表値が一致するかを個別に判定する。
- 一致するモデルは「**再現性あり**」と記録する。
- 一致しないモデルは「**再現性なし（既知の制約）**」と記録し、以下を併記する。
  - 一致しなかったケースの一覧
  - 代表値の差分
  - 試行間で生出力が一致しなかった組の件数
- **一致しないモデルが存在することを理由に、Phase 1 を未完了としない。** ただしその事実は仕様書およびレポートに明記する。

### 3.3 要件：仕様書への記載

`SPECIFICATION.md` 5.1 に以下を明記する。

- `seed` は全モデルに指定しているが、**再現性が保証されないモデルが存在する**
- 現時点で `gemini-3.1-pro-preview` は `temperature=0.0`, `seed=42` の指定下でも出力が変動する
- preview 版モデルは特に再現性が保証されないものとして扱う
- 再現性のないモデルについては、試行回数を増やすことで代表値の安定性を高める以外の対処がない

### 3.4 要件：レポートへの表示

- 実行条件サマリに「モデル別再現性ステータス」を掲載する。
- ステータスは `reproducible` / `not_reproducible` / `unverified`（2回実行の比較が未実施）の3値とする。
- `not_reproducible` のモデルのスコアには、代表値の信頼区間または試行間のばらつき（min/max）を併記する。

## 4. 打ち切り種別の区別

### 4.1 問題

打ち切り（`MAX_TOKENS`）には性質の異なる2種類がある。

| 種別 | 特徴 | 意味 |
| :--- | :--- | :--- |
| 思考起因 | `thoughts_token_count` が大きく、`candidates_token_count` が極小 | 測定条件の欠陥。可視出力の枠が思考に奪われている |
| 出力起因 | `thoughts_token_count` が 0 または小、`candidates_token_count` が上限付近 | 正当な打ち切り。出力そのものが長い |

現行の `truncated` フラグはこの2つを区別していない。是正後も出力起因の打ち切りは残りうるため、区別が必要である。

### 4.2 要件

- 打ち切りレコードに `truncation_type` を追加する。値は `thinking_dominant` / `output_dominant` / `unknown`。
- 判定基準および閾値は以下とする：
  - `truncated == true`（`finish_reason` が `MAX_TOKENS`, `MAX_OUTPUT_TOKENS`, `LENGTH`）の場合：
    - `thoughts_token_count > candidates_token_count` の場合：**`thinking_dominant`**（思考トークンが可視出力トークンを上回り、出力予算を圧迫して終了）
    - `thoughts_token_count` が `null` または `thoughts_token_count <= candidates_token_count` の場合：**`output_dominant`**（可視出力そのものが上限付近に達して終了）
  - `finish_reason` が取得不能（`null`）の場合：**`unknown`**
  - `truncated == false`（正常終了等）の場合：`null`
- 集計において、`truncation_rate` を種別（`overall`, `thinking_dominant`, `output_dominant`）ごとに分けて出力する。
- **`thinking_dominant` の打ち切りが 1 件でも存在する場合、そのカテゴリのスコアは能力の測定値として扱えない**旨をレポートに明記する。`output_dominant` については、出力長の制約下での挙動として解釈可能である。

## 5. 実施順序

1. §1 `max_output_tokens` の引き上げと `thinking_config` 対応
2. §4 `truncation_type` の実装
3. 再実行（`max_output_tokens=4096`、他の条件は前回と同一）
4. §1.3 打ち切りが 0% になったかの確認。ならなければ値を上げて再実行
5. §2 前回結果との比較表の出力
6. §3 再現性判定の見直し（再現性確認のため、同一条件でもう 1 回実行）

### 手順6についての注意

再現性確認には**同一条件での2回実行**が必要である。手順3で1回、手順6で1回、計2回の実行になる。手順4で値を変更して再実行した場合は、その値での2回実行が必要になる。

コストと所要時間は増加するが、再現性の確認は Phase 1 の完了条件であり省略しない。

### 追補 v5 の残タスクとの関係

追補 v5 §3（全モデル同点ケースの精査）および §4（考察レポートの修正）は、**本追補の完了後に実施する**。

理由：`reasoning_01` および `reasoning_03` が全モデル 0 点である原因が、ケース設計の不備なのか打ち切りなのか、現状では切り分けられない。打ち切りを除去した状態で精査しなければ、誤った判定を dataset に固定してしまう。
