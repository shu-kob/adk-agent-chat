# 📗 SPECIFICATION 追補 — 仕様書整合性の修正 (ADDENDUM v2)

本ドキュメントは `docs/SPECIFICATION.md` に対する**追補仕様（第2版）**である。

追補 v1（Phase 1〜3）の実装は完了しているが、`SPECIFICATION.md` 本体が実装に追従できておらず、記述の重複・矛盾・構成の不整合が残っている。本追補はその修正を指示するものであり、**新規機能の追加を含まない**。

## 本追補の位置づけと注意事項

- 対象は `docs/SPECIFICATION.md` の記述のみ。**ソースコードの動作を変更してはならない**。
- 修正はドキュメントの実態への同期であり、実装が仕様書と異なる場合は**実装を正とする**。ただし実装側に明確な誤りを発見した場合は、修正せず報告すること。
- 本追補の内容を反映後、`SPECIFICATION.md` の冒頭にある追補への参照リンクを更新し、本ファイルを追補一覧に加えること。

## 1. モデル識別子の統一

### 現状の問題

`SPECIFICATION.md` 内でモデル一覧が複数箇所に記載されており、内容が食い違っている。

| 箇所 | 現在の記載 |
| :--- | :--- |
| L31 付近（mermaid 図） | `gemini-3.7-flash` / `gemini-3.5-flash-lite` / `gemini-3.1-pro-preview` |
| L58 付近（技術スタック） | 同上 |
| L63 付近（技術スタック・重複行） | `gemini-2.5-flash`, `gemini-2.5-pro`, `gemini-3.5-flash-lite` 等 |
| L207 付近（評価対象） | `gemini-3.7-flash` / `gemini-3.5-flash-lite` / `gemini-3.1-pro-preview` |

### 確定した正の値

評価対象モデルは以下の3つで確定とする。

- `gemini-3.7-flash`
- `gemini-3.5-flash-lite`
- `gemini-3.1-pro-preview`

### 要件

- 上記と異なるモデル一覧の記載（`gemini-2.5-*` を含む行）を**すべて削除**する。
- 記載箇所を減らし、**評価対象モデルの一覧は「5.1 評価設計原則」の1箇所を正とする**。他の箇所（mermaid 図、技術スタック表）からは具体的なモデル名を削除し、「評価対象モデルは 5.1 を参照」と記述する。
  - 理由: 同じ情報を複数箇所に持つと、モデル追加のたびに同期漏れが発生する。今回の不整合の直接の原因がこれである。

### 「チャット既定モデル」と「評価対象モデル」の区別

以下は**別の概念であり、一致させる必要はない**。仕様書上でも混同されないよう明記すること。

| 概念 | 定義 | 現在値 |
| :--- | :--- | :--- |
| チャット既定モデル | `/api/chat` が使用するモデル。環境変数 `GEMINI_MODEL` で設定 | `gemini-3.5-flash-lite` |
| 評価対象モデル | ベンチマーク実行時に比較する候補の集合 | 上記3モデル |

3.2 環境変数仕様の `GEMINI_MODEL` の説明に「チャット機能で使用する既定モデル。評価対象モデルとは独立して設定される」旨を追記すること。

## 2. ディレクトリ構成の更新

### 現状の問題

「3.1 ディレクトリ構成」のツリーが追補 v1 実装前のままであり、以下の齟齬がある。

- `guard.py`, `precheck.py`, `aggregator.py`, `datasets/`, `traffic/` が記載されていない
- `dataset.py` に「評価データセット (全13ケース)」と注記されているが、実際にはデータセットは外部ファイルへ分離済みで、ケース数も30件以上に増えている

この不整合は、開発者および AI エージェントがツリーを実態と誤認する原因になる。

### 要件

`backend/` 配下のツリーを、**実際のファイル構成を確認したうえで**更新する。想定される構成は以下だが、実装と照合して差異があれば実装を正とすること。

```text
backend/
├── agent.py            # ADK Agent / Runner / Session 管理
├── config.py           # 環境変数読み込み・モデル設定
├── main.py             # FastAPI ルーティング・API エンドポイント
├── requirements.txt    # バックエンド依存パッケージ
├── .env                # 環境設定ファイル (Git 管理外)
├── .env.example        # 環境変数テンプレート
├── tests/              # バックエンド単体テスト
└── eval/               # LLM 評価基盤
    ├── dataset.py      # データセットローダー（定義本体は datasets/ 配下）
    ├── datasets/       # 評価データセット定義（外部化）
    │   └── benchmark_v2.json
    ├── evaluator.py    # 決定論的採点ロジック（アサーション単位）
    ├── precheck.py     # モデル事前疎通チェック
    ├── runner.py       # ベンチマーク実行
    ├── guard.py        # 集計時マージガード
    ├── aggregator.py   # 集計・レポート生成
    ├── results/        # 評価結果 (JSON / Markdown)
    └── traffic/        # 実トラフィック蓄積・リプレイ
        ├── store.py            # 蓄積
        ├── replay.py           # リプレイ実行ジョブ
        ├── diff_analyzer.py    # 決定論的差分分析
        └── data/               # 蓄積データ (Git 管理外)
```

各ファイルの注記は、実装の役割と一致させること。

## 4. 評価基盤の章構成の分割

### 現状の問題

「5.3 実トラフィックの蓄積とリプレイ評価仕様」が `## 5. LLM ベンチマーク評価基盤仕様` の配下に置かれている。

しかし追補 v1 で定義したとおり、この2つは**目的・入力・実行頻度の異なる別系統**である。同一章の中に置くと、読み手が「ベンチマークの一機能」と誤読する。

| 系統 | 目的 | 入力 | 実行頻度 |
| :--- | :--- | :--- | :--- |
| Golden dataset | 現行構成の劣化検知 | 固定データセット | デプロイ時・定期 |
| リプレイ評価 | 候補への切り替え判断 | 蓄積された実トラフィック | 検討期間のみ随時 |

### 要件

- 現行の `5.3` を独立章 `## 6. 実トラフィック蓄積とリプレイ評価基盤` として切り出す。
- 以降の章番号を繰り下げる（現行の `## 6. 仕様更新チェックリスト` は `## 7.` になる）。
- 新章 `## 6.` の冒頭に、上記の系統対比表を掲載し、**Golden dataset 系統との役割の違い**を明記する。
- 新章に以下の運用上の注意を追記する。
  - リプレイ評価は**常時稼働させるものではない**。候補の検討期間中のみ実行する
  - リプレイは蓄積されたトラフィックを前提とするため、**蓄積は評価の必要が生じる前から開始しておく必要がある**。過去のクエリを遡って取得することはできない

## 5. 補足記述の追加

実装済みの挙動のうち、仕様書に記載がないか、記載が不十分なものを補う。

### 5.1 seed 非対応モデルの扱い

「5.1 評価設計原則」に `seed=42` と記載があるが、`seed` パラメータをサポートしないモデルが存在しうる。実装の実際の挙動を確認したうえで、以下を明記する。

- サポートしないモデルに対してどう扱うか（指定を省略する / エラーとする）
- その場合に結果メタデータの `generation_config.seed` に何が記録されるか

実装が未対応の場合は、仕様書に「現時点では全対象モデルが `seed` をサポートしている前提。非対応モデルを追加する際は挙動の定義が必要」と制約として記載する。

### 5.2 PII マスキングの適用範囲

現行の `default_pii_masking_hook` はメールアドレスと電話番号のみを対象としている。

- 「6章（旧 5.3）」の該当箇所に、**現行実装はデモ・検証用途の範囲であり、本番トラフィックの蓄積に用いるには不十分**である旨を明記する。
- 未対応の代表例（氏名、住所、口座番号、社内固有の識別子など）を挙げ、本番適用時には対象の拡張が必要であることを注記する。

この注記がないと、将来の利用者が現行実装を本番適用可能と誤認するリスクがある。

### 5.3 蓄積データの Git 管理除外

`backend/eval/traffic/data/traffic_log.jsonl` にはユーザー入力が含まれる。

- `.gitignore` に該当パスが含まれているかを確認する。含まれていない場合は追加する。
- 「6章」の蓄積仕様に、**蓄積データは Git 管理対象外である**ことを明記する。
- ディレクトリ構成のツリーにも `(Git 管理外)` の注記を付ける。
